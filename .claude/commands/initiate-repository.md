---
description: Run the architect agent against docs/constitution.md, then implement the project structure it declares — every file written for real (constitution, then best_practices, then custom_implementations, then skills, in that priority order), including a working database-connected health check endpoint, a .env, and a runnable Docker/docker-compose setup (api/test/db services) — once approved.
---

Takes one required argument: the repository name (`$ARGUMENTS`), e.g. `/initiate-repository
payments-api`. This name becomes the project's identity throughout the scaffold — it replaces the
placeholder project name in `docs/constitution.md` and `docs/best_practices.md`, and is the path
segment the API is mounted under (e.g. `/api/<repository-name>/v1/...`).

This command does not create empty placeholder files. Every file `## Structure` declares is
implemented with real content, decided by checking these sources **in this order** and stopping at
the first one that actually decides the file's content — do not fall through to a later source for
something an earlier one already settled, and do not skip ahead past one that doesn't apply instead
of checking it:

1. `docs/constitution.md` — `## Stack`, `## Conventions`, and anything it explicitly requires (e.g.
   the health check endpoint, `.env`).
2. `docs/best_practices.md` — apply the "Example code after" shape of whichever numbered pattern
   matches the file's role (e.g. a domain exception file follows Pattern 6, a router file follows
   Pattern 5, etc.).
3. `docs/custom_implementations/` — reuse `CustomException`, `@requires_permissions`,
   `@with_transaction` rather than reimplementing an equivalent when a file needs one of these.
4. The relevant `.claude/skills/*/SKILL.md` for anything the three sources above leave undecided
   (e.g. `architecture/SKILL.md` for layering, `naming/SKILL.md` for identifiers,
   `dependency-injection/SKILL.md` for wiring, `testing/SKILL.md` for test file shape).

`docs/constitution.md` is authored by a human before the repo exists in any real sense — it is not
generated by this command, and there is no skill governing its format for the same reason a mission
spec has one: nothing upstream of it produces it. Its expected shape:

```markdown
# <project-name>

<one-paragraph description of what this project is>

## Stack

- Language: <language + version>
- Framework: <web framework / build tool, if any>
- Package manager: <npm / pip / poetry / uv / ...>

## Structure

​```text
src/
src/domain/
src/application/
src/infrastructure/
tests/
README.md
pyproject.toml
​```

## Conventions

<optional free-text notes: architecture style, naming rules, anything a human or agent scaffolding
this repo for the first time should know.>
```

## 1. Resolve the repository name

- Take the repository name from `$ARGUMENTS`. If it is empty, ask the user for it before doing
  anything else — do not invent one or fall back to a directory name.
- Expect a short, kebab-case slug (e.g. `payments-api`); if what was given isn't, ask the user to
  confirm or correct it rather than silently normalizing it.

## 2. Locate the constitution

- Read `docs/constitution.md` at the repository root.
- If it does not exist, stop and tell the user to add one before running this command again, using
  the template above. Do not fabricate one yourself.

## 3. Personalize the example docs

`docs/constitution.md` and `docs/best_practices.md` ship with a placeholder project name standing
in for a real one. Replace it with the resolved repository name from step 1, and nothing else in
either file:

- In `docs/constitution.md`, replace the top-level title (`# <placeholder>`) with
  `# <repository-name>`.
- In `docs/best_practices.md`, replace the top-level title (`` # `<project>` - Best Practices ``)
  with `# <repository-name> - Best Practices`, and replace every `/api/<project>/...`-shaped
  endpoint path with `/api/<repository-name>/...`.
- If a file no longer contains the placeholder (e.g. this command already ran once for this repo),
  leave it untouched and note that in the report rather than erroring.

## 4. Architecture gate

- Dispatch the `architect` agent (`.claude/agents/delivery/architect.md`) with task id `constitution`.
  Unlike a normal task, there is no `.claude/tasks/constitution/specs/constitution.md` mission spec —
  pass the `docs/constitution.md` path directly as the input instead, and tell the agent so
  explicitly (this is a deliberate, one-off deviation from its usual input location, not an error).
- The architect still produces its two usual deliverables under `.claude/tasks/constitution/plan/`:
  `plan.md` (the implementation plan for scaffolding this structure) and `architecture-gate.md` (the
  17-section decision document, per `.claude/skills/artifacts/SKILL.md`). Tell the architect that
  `plan.md` must cover, for every **file** line in `## Structure` (not just the directories), what
  that file implements and which of the four priority sources above decides it — plus (a) the health
  check endpoint's design (how it verifies the database connection and what it returns when healthy
  vs. not, given `## Stack`), (b) which environment variables the project needs at minimum to run
  (at minimum the database connection string), and (c) the Docker setup: `Dockerfile`'s build
  stages, and `docker-compose.yml`'s `api`/`test`/`db` services per `## Conventions` — so the
  Developer in step 7 has a concrete, per-file design to implement rather than inventing one
  unreviewed.
- **Stop here.** This is an approval gate like any other in the pipeline (see `CLAUDE.md`): report
  the path to `architecture-gate.md` and wait for the human to approve before scaffolding anything.
  Do not proceed to step 5 on your own.

## 5. Parse the structure

Once the human has approved:

- Extract the fenced ```text block under `docs/constitution.md`'s `## Structure` heading.
- Skip blank lines and `#`-prefixed comments inside the fence.
- Classify each remaining line: trailing `/` → directory, otherwise → file.
- If `## Structure` or its fence is missing/empty, stop and report that rather than guessing a
  structure from the rest of the document.

## 6. Create directories

- Create every directory line from step 5, in the order listed.
- Do not add `.gitkeep` yet — wait until step 7 is done, so it's only added to a directory that
  genuinely ends up with no implemented file inside it.

## 7. Implement every file

- Dispatch the `developer` agent (`.claude/agents/delivery/developer.md`) with task id
  `constitution`, pointing it at `.claude/tasks/constitution/plan/plan.md` (from step 4) as the
  approved, per-file design — the same handoff shape any other developer dispatch gets, just sourced
  from this one-off plan instead of a normal task's.
- For every file line from step 5, it writes real content per the priority order and plan.md's
  per-file decision — no file from `## Structure` is left empty or a stub.
- It implements the health check endpoint for real (only if `## Conventions` declares the
  requirement, as this repo's own `docs/constitution.md` does): a route mounted under
  `/api/<repository-name>/v1/...` (per step 3) that checks the database connection (and any other
  critical dependency `## Conventions` names) and returns the healthy/unhealthy response shape
  `plan.md` specifies — not a stub that always returns `200`.
- It creates `.env` at the repository root defining, at minimum, the database connection variable
  the health check reads, plus any other variable `plan.md` calls out as required to run the
  project — placeholder/local-dev values, never a real secret. If `.gitignore` excludes `.env` (this
  repo's does), also create a tracked `.env.example` with the same keys so the project is runnable
  from a fresh clone after copying it.
- It implements a runnable Docker setup per `## Conventions` (only if the constitution declares the
  requirement, as this repo's own `docs/constitution.md` does): a multi-stage `Dockerfile`, and a
  `docker-compose.yml` with three services — `api` (built from `Dockerfile`, reads `.env`, waits on
  `db`'s healthcheck, runs migrations then starts the server, mirroring `entrypoint.sh`), `test`
  (same image as `api`, entrypoint overridden to run the test suite against `db`), and `db` (the
  project's database engine with a healthcheck and a named volume) — `docker compose up` must work
  against what gets written here, not just look plausible.
- Add a `.gitkeep` to any directory from step 6 that still has no file in it after all of the above.
- Never overwrite a path that already has real content — skip it and note it in the report instead.

## 8. Verify completeness

Repository initiation is not complete just because steps 3, 6 and 7 ran without error — check every
one of these before reporting success, and if any fails, say so explicitly in the report rather than
silently calling the run done:

- `docs/constitution.md` and `docs/best_practices.md` no longer contain the placeholder project
  name — the resolved repository name from step 1 appears in both titles, and in every API path in
  `docs/best_practices.md`.
- Every path listed under `## Structure` exists on disk now, whether created this run or already
  present beforehand — re-read the constitution's path list and confirm each one, don't just trust
  steps 6–7's own bookkeeping.
- Every **file** path has real, non-empty content — not a `touch`-equivalent placeholder. For a
  sample spanning each layer (domain/application/infrastructure/tests), name which of the four
  priority sources decided its content.
- Every directory that still has no file in it has its `.gitkeep`.
- If `docs/constitution.md`'s `## Conventions` declares a health check requirement, a corresponding
  module (e.g. `src/health/`) is present among the verified paths, AND it contains a real
  implementation per step 7 — not just empty structure. Flag this gap explicitly if `## Conventions`
  asked for a health check but `## Structure` omitted the module, or if step 7 was
  skipped/incomplete.
- `.env` (and `.env.example` when `.env` is gitignored) exists and defines every variable the health
  check and `plan.md` call out as required — not an empty file.
- If `## Conventions` declares a Docker requirement, `docker-compose.yml` defines all three
  services it asks for (`api`, `test`, `db`) with the dependencies described (`api`/`test` wait on
  `db`'s healthcheck, `db` has a healthcheck and a named volume), and `Dockerfile` has distinct
  build stages — not an empty or stub file. Flag this gap explicitly if any service is missing or
  if the files exist but are empty.
- No path outside the declared `## Structure` list, step 7's health-check/`.env`/Docker outputs, and
  this command's own outputs (`.claude/tasks/constitution/...`) was created or modified.

## 9. Report

List, in order:
- The resolved repository name, and what was personalized with it in step 3.
- Directories created.
- Files implemented, each with the priority-source tier (constitution / best_practices /
  custom_implementations / skill name) that decided its content.
- Paths skipped because they already had real content.
- Whether the health check endpoint and `.env`/`.env.example` were implemented, and what they
  contain (route path, variables defined) — or why they were skipped.
- Whether the Docker setup was implemented, and what it contains (`docker-compose.yml`'s services
  and their dependencies, `Dockerfile`'s stages) — or why it was skipped.
- The result of each completeness check from step 8, including any gap found.

Do not commit anything — scaffolding is a working-tree change only. Leave committing to the user or
to `/ship`.
